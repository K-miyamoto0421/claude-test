# /goal コマンド リファレンス

`goal-prompt-composer` スキルが条件文を組み立てる際に参照する詳細資料。

## /goal コマンドの仕様

`/goal <条件>` は、指定した条件が満たされるまでClaudeが自動的に複数ターンの作業を
繰り返す機能。各ターンの終了後、小型モデル（デフォルトHaiku）が条件を満たしたかどうかを
チェックし、未達成であれば自動的に次のターンへ進み、達成していれば停止する。

参考: [Keep Claude working toward a goal - Claude Code Docs](https://code.claude.com/docs/en/goal)

## 良い条件文の3要素

効果的な `/goal` の条件文は、次の3つを満たす。

### 1. 測定可能な終了状態

Claude（を評価する小型モデル）が「YesかNoか」を客観的に判定できる状態であること。

- 良い例: `npm test exits 0`、`テストが全てパスする`、`git status is clean`、
  `ビルドが成功する`、`lintエラーが0件になる`
- 悪い例: `いい感じにする`、`もっと良くする`、`きれいにする`
  （何をもって「良い」「きれい」とするかが判定不能）

### 2. 確認方法の明示

Claudeがどうやってその状態を確認すべきかの手がかりを条件文に含める。

- 例: `npm test を実行して確認する`、`pytest で確認する`、`ビルドコマンドを実行して確認する`
- これがないと、Claudeが確認手段を自己流で選び、意図と異なる基準で「完了」と判断する
  リスクがある。

### 3. 制約条件

やってはいけないこと・触ってはいけない範囲を明示する。

- 例: `他のテストファイルは変更しない`、`〇〇ディレクトリ配下のみ変更する`、
  `既存のAPIインターフェースは変更しない`
- 制約がないと、終了条件を満たすためだけに無関係な変更（テストの削除・スキップなど）を
  してしまうリスクがある。

## ターン数の上限

範囲が広い、あるいは自動継続が長引くリスクがある場合は、末尾に上限を付けられる。

```
/goal <条件> or stop after 20 turns
```

## 良い条件文の例（全体）

```
/goal all tests in test/auth pass and the lint step is clean
```

```
/goal test/auth 配下のログイン関連テストが全てパスする。npm test で確認する。
test/auth 以外のファイルは変更しない。
```

## 曖昧で使うべきでない条件文の例

- `プロジェクトをいい感じにして` → 終了状態が不明
- `バグを直して` → どのバグか、直った基準が不明
- `パフォーマンスを改善して` → 測定方法・目標数値がない

これらのパターンが音声入力から検出された場合、`goal-prompt-composer` スキルは
AskUserQuestionツールでユーザーに具体的な終了条件を確認する。

## 関連機能との違い

- **`/loop`**: 時間間隔ベースで繰り返す。条件充足ベースではない点が `/goal` と異なる。
- **Stop hook**: `settings.json` でカスタム評価ロジックを組みたい場合向け。`/goal` より
  柔軟だが設定コストが高い。
