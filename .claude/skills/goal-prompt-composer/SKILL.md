# goal-prompt-composer

音声入力由来の口語的な要望文を、`/goal <条件>` にそのまま貼り付けて実行できる
1行のプロンプトに変換する。`/goal` の仕様と良い条件文の書き方は `reference.md` を参照。

## なぜこのスキルが必要か

`/goal` は「条件が満たされるまで自動でターンを繰り返す」機能であり、条件文の質がそのまま
自動実行の質に直結する。一方、音声入力はフィラー（「えーっと」「なんか」）・言い淀み・
話題の脱線・複数要求の混在を含みやすく、そのまま `/goal` に渡すと曖昧な目標判定になり
無限にターンが続いたり、意図と違う条件で止まったりする。このスキルは、その変換作業を
毎回人力でやらずに済むようにする。

## 手順

1. **口語的な入力を受け取る**
   ユーザーの発話（音声認識テキスト）をそのまま受け取る。フィラー・重複・言い淀みが
   含まれていても気にせず、まず意味内容の把握に集中する。

2. **フィラーと脱線を除去し、意図を整理する**
   「えーっと」「なんか」「その、あの」等のフィラーや、本題と関係ない雑談部分を除いて、
   実際にやってほしいことだけを箇条書きレベルで洗い出す。

3. **3要素を抽出する（詳細は `reference.md`）**
   - **測定可能な終了状態**: 何がどうなったら完了と言えるか（客観的にYes/No判定できる状態）
   - **確認方法**: Claudeがどうやってその状態を確認すべきか（テスト実行、lint実行、git statusなど）
   - **制約条件**: やってはいけないこと・触ってはいけない範囲

4. **測定可能な終了状態が読み取れない場合は、AskUserQuestionツールで確認する**
   音声入力は「なんかいい感じにしてほしい」のような曖昧な着地になりがちである。
   終了条件を勝手に創作せず、聞き取れた内容から2〜3個の具体的な候補を提示して選んでもらう、
   または自由記述で確認する。曖昧なまま `/goal` プロンプトを生成しないこと。

5. **複数の要求が混在している場合は整理する**
   「バグも直したいしログインのところも直したい」のように複数要求が混じっている場合、
   単一の終了条件にまとめられるか（例: 両方のテストが通る）を検討する。まとめきれない、
   または優先順位が不明な場合はユーザーに確認する。

6. **`/goal` プロンプトを1行で出力する**
   そのままコピー&ペーストして実行できる形式で提示する。
   ターン数の上限を付けたほうがよさそうな場合（範囲が広い・自動継続のリスクがある等）は
   `or stop after N turns` を末尾に添える。

   ```
   /goal <測定可能な終了状態を確認方法・制約条件とともに1文にまとめたもの>
   ```

7. **一言で3要素の対応を添える**
   生成したプロンプトのどの部分が「終了状態」「確認方法」「制約」に対応しているかを
   簡潔に説明する（長い解説は不要、1〜2行程度）。

## 出力例

**入力（音声由来、口語的）**:
> えーっと、ログイン機能のテストが今落ちてて、それを直したいんだけど、他のところは触らないでほしくて。直ったかはテスト実行すればわかると思う。

**出力**:
```
/goal test/auth 配下のログイン関連テストが全てパスする。npm test で確認する。test/auth 以外のファイルは変更しない。
```
（終了状態＝テストが全てパス、確認方法＝npm test、制約＝test/auth以外は変更しない、に対応）

**入力（終了状態が不明瞭な例）**:
> なんかこのプロジェクト全体もうちょっといい感じにしてほしいんだよね

→ この場合は終了状態が特定できないため、AskUserQuestionで
「どの部分を」「どうなったら完了とするか」を具体的に確認してから組み立てる。
